## Context

The zimi-rs codebase (a Rust Cross-ZIM search/serve platform with Postgres FTS, semantic search, and qBittorrent integration) underwent a full 7-agent themed review. The codebase is in strong shape — no critical or high-severity security vulnerabilities were found. The review identified 4 high-priority findings, ~20 medium/low findings, and several ponytail-level simplifications. This plan addresses every finding except the two explicit exclusions.

**Key architectural facts that shape the plan:**
- `SqlQuery.params` is `Vec<String>` — all SQL parameters are bound as `text` to Postgres.
- `SettingsCache` uses an `RwLock<HashMap>` with a generation counter; snapshots read under a single lock pass.
- `AppState` is an 8-field shared struct passed to all axum handlers via `State<AppState>`. Adding a field requires updating all 7 constructor sites: `main.rs:235`, `serve/handlers_test.rs` ×5, `mcp/mod.rs:565`.
- The download poller is a single tokio task; blocking work is offloaded via `spawn_blocking`.
- The web UI is 3 static HTML files + 1 JS file, no build step.
- `general.cors_origins` is `config_only: true` in `SETTING_DEFS` — intentionally startup-only, not a runtime setting. The M-6 finding is a non-issue by design.
- `RwLock` guards must be dropped before any `.await` (the codebase enforces this at `cache.rs:439`). Any new mutex held across awaits must be `tokio::sync::Mutex`, not `std::sync::Mutex`.

#### WI-8: Batch `reconcile()` DB operations
**Finding:** P-3
**File:** `src/torrent/poller/reconcile.rs`
**Issue:** `reconcile()` issues individual `UPDATE` statements per row (hash rebind, error marking, seeding refresh, etc.) — an N+1 pattern.
**Scope note:** The `downloads` table is small (typically < 1000 rows), so this is a performance optimization, not a correctness fix.
**Fix:** Collect the per-row changes and batch them into fewer statements:
- [ ] Collect all hash rebinds into a single `UPDATE ... FROM (VALUES ...)` or a loop with `UNIQUE` constraints
- [ ] Collect all seeding stat refreshes into a single batch
- [ ] The adoption INSERT is already guarded by `WHERE NOT EXISTS`, so it's safe as-is
- [ ] The `handle_complete` calls (file I/O) must remain individual — they're not batchable

**Practical approach:** Rather than complex batch SQL, use a single `UPDATE ... WHERE id = ANY($1)` for the simple status transitions, and keep the `handle_complete` calls individual. The hash rebinds and seeding stat refreshes can each be one batched statement.
