# zimservice

Cross-ZIM search and serve platform written in Rust.

## Features

- **Hybrid search** — Postgres FTS + pg_trgm fuzzy matching + optional pgvector semantic search
- **Multi-ZIM** — Search across all installed ZIM archives simultaneously
- **Q-ID linking** — Wikidata cross-language article resolution
- **qBittorrent integration** — Download ZIMs via torrent with hardlink-based file sharing
- **MCP server** — AI agent integration via Model Context Protocol (stdio)
- **Web UI** — Library view, search page, settings management
- **OpenAI-compatible embeddings** — Semantic search via any /v1/embeddings endpoint

## Quick Start

### With Docker

```bash
AUTH_PASSWORD='<a real admin password>' docker compose up -d
```

> Compose runs in **password mode** and refuses to start with an empty or
> placeholder `AUTH_PASSWORD` (shell-level `:?` fails fast before the container
> starts). The HTTP port is published on loopback only (`127.0.0.1:8899`).

> **Note:** this service **requires the [pgvector](https://github.com/pgvector/pgvector) Postgres extension** — the initial migration (`CREATE EXTENSION vector`) runs unconditionally, so a stock `postgres` image fails at migration on first boot. The compose file uses the `pgvector/pgvector:pg16` image to provide it.

> A `.dockerignore` keeps the build context lean (excludes `target/`, `.git/`, `plans/`, `docs/`, etc.) so the image build doesn't ship build artifacts or VCS state.
>
> **Production:** the dev compose exposes Postgres at `127.0.0.1:5432` with fixed dev credentials (`zimservice`/`zimservice`) for convenience only. For production, set `POSTGRES_PASSWORD` via `.env`, restrict the port mapping accordingly, and update the `DATABASE_URL` used by `make test-integration` (Makefile) and `tests/integration.rs` (`DEFAULT_URL`) — both currently hardcode the dev credentials.

### Manual

1. Start Postgres with pgvector:
```bash
docker run -d --name zimservice-pg \
  -e POSTGRES_USER=zimservice \
  -e POSTGRES_PASSWORD=zimservice \
  -e POSTGRES_DB=zimservice \
  -p 5432:5432 \
  pgvector/pgvector:pg16
```

2. Build and run:
```bash
cargo build --release
ZIM_DIR=./zims DATABASE_URL=postgres://zimservice:zimservice@localhost:5432/zimservice \
  ./target/release/zimservice serve
```

3. Open http://localhost:8899

## CLI

```
zimservice serve          # Start HTTP server
zimservice list           # List ZIM archives (read-only; --sync to reconcile DB with disk)
zimservice status         # Show server status
zimservice index --all    # Index all ZIMs
zimservice index -z name  # Index specific ZIM
zimservice mcp            # Run MCP server on stdio
zimservice embed -z name  # Generate embeddings
```

## API

| Endpoint | Method | Description |
|----------|--------|-------------|
| `/health` | GET | Health check (returns `200` when the DB is reachable, `503` when the DB is down; the body always reports the real `db_connected`/`qbit_connected` probes) |
| `/list` | GET | List ZIM archives |
| `/search?q=...` | GET | Hybrid search (`total` is the returned page length, not a corpus-wide match count) |
| `/suggest?q=...` | GET | Title autocomplete |
| `/read?zim=...&path=...` | GET | Read article as text |
| `/w/{zim}/{path}` | GET | Raw content (HTML) |
| `/chunks?zim=...&path=...` | GET | RAG text chunks |
| `/interlanguage?zim=...&path=...` | GET | Cross-language links |
| `/snippet?zim=...&path=...` | GET | Indexed snippet + preview |
| `/random?zim=...` | GET | Random article |
| `/settings` | GET/PUT | Settings CRUD |
| `/settings/zim/{name}` | GET/PUT | Per-ZIM settings |
| `/downloads` | GET/POST | Download management |
| `/downloads/{id}` | DELETE | Cancel a download |
| `/collections` | GET/POST | List / create ZIM collections |
| `/collections/{id}` | PUT/DELETE | Update / delete a collection |
| `/openapi.json` | GET | Generated OpenAPI 3.1 spec (utoipa) |

The API is rate-limited (token bucket, service-wide). The bucket is **shared by all clients by design** (single-operator model — see Threat model); one heavy client can 429 every other client. Defaults: `access.rate_limit_rps = 100`,
`access.rate_limit_burst = 200`. Exceeding the limit returns `429 Too Many Requests` with a
`Retry-After` header. `/health` is exempt. The OpenAPI spec is generated by
[utoipa](https://docs.rs/utoipa) from `#[utoipa::path]` attributes on the handlers.

## Configuration

Startup/process settings come from environment variables and compiled-in
defaults (there is no config file).

Runtime settings (search weights, embedding endpoint/model, torrent behavior,
rate limits, CORS origins, access mode) live in the `settings` table and are
managed via the web UI at `/settings.html` — they change without a restart.

### Environment variables

| Variable | Default | Description |
|----------|---------|-------------|
| `ZIM_DIR` | `/zims` | Directory containing `.zim` files |
| `DATABASE_URL` | `postgres://localhost:5432/zimservice` | Postgres connection string (see note below) |
| `DB_POOL_SIZE` | `20` | Postgres connection pool size |
| `HOST` | `127.0.0.1` | HTTP bind address (use `0.0.0.0` only behind a reverse proxy or with `access.mode=password`) |
| `PORT` | `8899` | HTTP listen port |
| `LOG_LEVEL` | `info` | `tracing` level (or `RUST_LOG`) |
| `AUTH_PASSWORD` | (none) | Sets the admin password; locks `access.admin_password` |
| `ACCESS_MODE` | (none) | Sets `access.mode` (`open` or `password`) |
| `QBITTORRENT_URL` | (disabled) | qBittorrent WebUI URL; its presence enables torrent support |
| `QBITTORRENT_USER` | (none) | qBittorrent username (optional; some installs run without auth) |
| `QBITTORRENT_PASS` | (none) | qBittorrent password (optional; some installs run without auth) |
| `EMBEDDING_ENDPOINT` | (none) | OpenAI-compatible `/v1` URL; seeds `embedding.endpoint` |
| `EMBEDDING_API_KEY` | (none) | Seeds `embedding.api_key` |
| `EMBEDDING_MODEL` | (none) | Seeds `embedding.model` |
| `EMBEDDING_DIM` | (none) | Seeds `embedding.dimension` |

`AUTH_PASSWORD`, `ACCESS_MODE`, and the `EMBEDDING_*` vars seed the corresponding
settings at startup (the env value wins) and lock them in the UI.

`DATABASE_URL` accepts `postgres+tls://` / `postgresql+tls://` and the `sslmode`
parameter for readability; the `+tls` scheme is rewritten to the plain form the
driver accepts before use, and TLS is applied per `sslmode` (`require` /
`verify-ca` / `verify-full` enable TLS, `disable` / `off` do not).

### Web routes

| Route | Description |
|-------|-------------|
| `/` | Library view (installed ZIMs) |
| `/search.html` | Search UI |
| `/settings.html` | Settings management UI |

### CORS

CORS is controlled by the `general.cors_origins` setting (a comma-separated origin
allowlist, e.g. `https://a.example,https://b.example`), applied at startup. With an
empty list no `Access-Control-Allow-Origin` header is emitted at all (browsers enforce
same-origin; `curl`, the embedded UI, and MCP are unaffected). When set, only the
listed origins, the methods `GET/POST/PUT/DELETE/OPTIONS`, and the headers
`Authorization`, `Content-Type`, `Range` are allowed.

## Security

### Security model

zimservice follows a **public-read / private-write** trust model. In both access modes,
all GET reads (including raw ZIM content via `/read` and `/w`) are publicly accessible
by design — this keeps the web UI and any read-only client working without
authentication. Writes and mutations are what the access mode controls. In
password mode, public reads are the **deliberate default**
(`access.require_auth_for_reads = false`), not an oversight: read content is
treated as non-sensitive; enable the flag to gate reads.

The server binds to **`127.0.0.1` (loopback) by default**. This is a deliberate
security choice: with no authentication in open mode, only local processes can reach
the API.

### Access control

- **`access.mode = "open"`** (default): all requests are open by design — anyone who
  can reach the server can read content and mutate settings. The server **refuses to
  start** if open mode is combined with a non-loopback bind (e.g. `0.0.0.0`), since
  that would expose the entire API to any network peer without authentication.
  Public `GET /settings` stays open in both modes (read-only view; secrets are
  redacted), but **mutating security-sensitive keys** (auth settings, SSRF policy,
  qBittorrent/embedding endpoints and credentials) is **forbidden with 403 while
  unauthenticated** — those require password mode.
- **`access.mode = "password"`**: mutating requests (POST/PUT/PATCH/DELETE) require the
  admin password; all reads (GET/HEAD/OPTIONS) remain open so the web UI and read-only
  clients can load without a token — by design (see Threat model). A blank password in password mode is a **startup
  error** (fail closed).

**Admin password storage.** `access.admin_password` is stored as an **argon2id**
hash (PHC format `$argon2id$v=19$m=19456,t=2,p=1$…`). Legacy `sha2:` hashes and
legacy plaintext values still verify and are transparently re-stored as argon2id
on the next successful auth. Note
that `torrent.password` and `embedding.api_key` are **not** hashed — they are sent
verbatim to qBittorrent / the embedding provider, so the settings table (and its
backups) must be treated as sensitive in both access modes.
Legacy plaintext passwords and older `sha2:` hashes are **deprecated**: both still
verify and are transparently re-hashed to argon2id on the next successful auth.
Removal deadline: **2027-08-30** — after that, plaintext verification will be
removed and a settings table still holding a non-`$argon2id$` value will fail
closed. Check your instance with `SELECT value FROM settings WHERE key =
'access.admin_password' AND value NOT LIKE '$argon2id$%'`.

**`GET /downloads`** redacts credentials from torrent URLs, but `file_path` reveals
server-local paths (where downloaded files land) — expected for the operator-facing
file-status UI, relevant if the API is exposed beyond the operator.

### Threat model

Be explicit about what each access mode protects:

- **Open mode** — the listener is trusted: every endpoint, including all writes,
is reachable by any network peer. Open mode is rejected at startup on a
  non-loopback bind for exactly this reason.
- **Password mode (default read behavior)** — only **mutating** requests are
  gated. All `GET`/`HEAD`/`OPTIONS` are readable by anyone who can reach the
  listener: ZIM article content, article text, `/w/` raw content, and the
  settings topology (secrets and internal endpoints redacted, but the *shape*
  of the configuration — models, batch sizes, category names — is visible).
  Treat the network position of the listener as the trust boundary. Public
  reads are the documented default (`access.require_auth_for_reads = false`);
  set it to `true` to gate them.
- **Password mode + `access.require_auth_for_reads = true`** (M1) — reads are
  gated too. Consequences:
  - **Known limitation:** the web UI's article links are plain `<a href="/w/…">`
    anchors — a new-tab navigation that cannot carry the Bearer header. With
    the flag on, clicking an article link 401s until the UI is changed to
    fetch raw content via the token-attached `apiFetch` and open a blob URL
    (deferred UI enhancement). Everything else in the UI keeps working: pages
    still load, and every JS data call attaches the token from sessionStorage
    (with a 401 re-prompt fallback).
  - Third-party clients that read-only-scrape the API break by design — that
    is the flag's purpose. Default-off keeps existing deployments unchanged.
- **Token-verification cache (M3)** — a successfully verified token is cached
  for 60s to avoid re-running the 100k-iteration hash per request. The cache
  is cleared on `reload()` (env/config change — the only realistic password
  change, since `access.admin_password` is API-immutable) and on `update()` /
  `upgrade_password()` as defense in depth. Worst case without a reload, a
  changed password takes effect within the 60s TTL.
- **Service-wide rate limit** — the token bucket is intentionally not per-client:
  with a single operator, per-client tracking is overkill, and the accepted
  trade-off is that one heavy client can 429 everyone. Raise
  `access.rate_limit_rps` / `access.rate_limit_burst` rather than expecting
  per-IP fairness.
- **Auth lockout is per source IP (no reverse-proxy support)** — the
  brute-force lockout keys on the raw TCP peer address and does **no**
  `X-Forwarded-For` parsing: the service expects direct (e.g. loopback)
  connections and does not support reverse proxies, where every client behind
  one proxy would share that proxy's IP (and thus lock each other out).
- **`?access_token=` query string** — accepted **only on read-only requests
  (GET/HEAD/OPTIONS)**; mutating requests must use `Authorization: Bearer`.
  Tokens in query strings can leak via server-side logs, proxies, and
  `Referer` headers. `sanitize_uri_for_logs` strips the param from *our*
  request logs, but reverse-proxy / load-balancer access logs are out of our
  control — prefer `Authorization: Bearer` wherever possible. The server
  speaks plain HTTP; terminate TLS at a reverse proxy before exposing it
  beyond loopback.

### MCP server authentication

The MCP stdio server inherits the same access model. When `access.mode = "password"`,
the MCP server requires the `MCP_AUTH_PASSWORD` environment variable to match the
configured admin password before it will start. Without a matching password the MCP
server refuses to start (fail-closed).

The password is presented as `Authorization: Bearer <password>` (preferred for
programmatic clients), or as `?access_token=<password>` on read-only requests
(browser embeds). The query-string form is ignored on mutating requests and is
exposed in server logs and `Referer` headers — prefer the Bearer header
wherever possible.

### Download SSRF protection

Direct `.zim` downloads and torrent fetches are guarded against SSRF:
- The redirect policy re-validates **every** hop, so a `302` to a private or
  metadata IP fails the download instead of following it.
- For direct downloads the host is resolved and **pinned** for the fetch, closing the
  DNS-rebinding time-of-check/time-of-use window.
- Resolved IPs are checked against the private/reserved-range policy. The
  `downloads.allow_private_networks` setting (default `false`) controls whether
  private/LAN/metadata addresses are permitted; by default they are blocked.
- The **qBittorrent Web API** is guarded by the same policy. If your qB instance
  lives on a private/LAN host (e.g. `http://192.168.0.25:8080`), it is blocked by
  default; opt in with the `torrent.allow_private_networks` setting (default
  `false`). Loopback (`localhost`) is always admitted for a local qB install, and
  the always-blocked ranges (cloud-metadata `169.254.169.254`, link-local, IETF-doc,
  NAT64) stay blocked even with the opt-in. Flipping it reconnects the client on
  the next poll tick (no restart).
- Downloaded files pass a **structural check** (`zim::Zim::new` parse) but
  **no checksum verification** — the `zim` 0.5 library exposes no
  checksum/signature API and OPDS catalogs carry no hashes to compare against.
  A structurally valid but tampered or malicious ZIM therefore **parses and is
  served**: there is no end-to-end byte authentication, so trust = pinned
  sources + (https) TLS. Trust the download sources (torrent trackers, OPDS
  URL, user-supplied URLs) the way you would trust a browser download.

### Served content

`/w` (raw ZIM content) sets `X-Content-Type-Options: nosniff`, and for
`text/html` responses also a sandboxing `Content-Security-Policy`
(`default-src 'none'; script-src 'none'; style-src 'unsafe-inline'; img-src
data: blob:; font-src data:; frame-ancestors 'none'`) plus `X-Frame-Options:
DENY`. This deliberately breaks ZIM entries that rely on inline scripts: a
served article must not run same-origin JavaScript (it could read the admin
token from `sessionStorage` and call the settings API); inline styles and
data-URI images keep rendering.

The embedded Web UI pages (`/`, `/search.html`, `/settings.html`,
`/common.js`) set their own permissive baseline (they use inline
scripts/styles by design): `Content-Security-Policy` (`default-src 'self'`
with `'unsafe-inline'`), `X-Frame-Options: DENY`, `Referrer-Policy:
no-referrer`.

### ZIM content trust boundary

`verify_zim` checks **structural integrity only** (the file parses as a valid
ZIM). It does NOT verify content provenance: no cryptographic signature is
checked. Your trust boundary is the **source** (OPDS feed URL, torrent
tracker), not the file itself. For high-trust deployments, pin torrents by
hash and/or verify the OPDS feed over TLS with a known-good endpoint.

### TLS termination

zimservice speaks plain HTTP. For network-facing deployments (password mode +
non-loopback bind), terminate TLS at a reverse proxy (Caddy, nginx, etc.) and
point the proxy at `127.0.0.1:<port>`. The server warns at startup when it
detects a non-loopback bind in password mode.

### Trusted proxy IPs (lockout)

When zimservice sits behind a reverse proxy, all requests appear to come from
the proxy's IP. Set `general.trusted_proxy_cidrs` (comma-separated CIDRs,
e.g. `10.0.0.0/8,192.168.1.0/24`) or the `TRUSTED_PROXY_CIDRS` env var to the
proxy's source range. When set, the auth lockout walks the
`X-Forwarded-For` header right-to-left, skipping trusted CIDRs, to identify
the real client IP. Without this setting, the lockout keys on the proxy IP
(everyone shares one bucket). This is a config-only setting (restart
required).

### Index checkpoints

Indexing checkpoints are transient JSON (ZIM name + resume counters) written to
a **pid-scoped** subdirectory under the system temp dir (SEC low). They contain
no secrets, and the per-process scoping means two processes can never share (or
clobber) a checkpoint path for the same ZIM name.

## Architecture

```
zimservice
├── axum HTTP server (REST API + embedded web UI)
├── Postgres (FTS + trgm + pgvector)
├── ZIM file reader (zim crate, memmap + zstd)
├── Text extraction (deformat crate, SIMD)
├── Parallel indexing (rayon)
├── qBittorrent client (reqwest)
├── Embedding pipeline (OpenAI-compatible API)
└── MCP server (stdio, JSON-RPC 2.0)
```

```sh
make build       # debug build
make release     # optimized build (LTO + strip)
make install     # install to ~/.local/bin
make test        # full test suite (skip-tolerant for integration tests)
make test-fast   # lib + bin tests only, no integration tests

```

The `plans/` directory holds review / research / deep-plan process artifacts —
the process record of design decisions and their rationale. It is not shipped in
the binary: the build only embeds migrations via `include_str!` and the static
`web/` UI.

**Formatting.** The 100-char line limit is enforced by `cargo fmt` (rustfmt,
`max_width = 100` in `rustfmt.toml`) on Rust code only. `web/` (JS) and the
`migrations/` SQL are exempt — line length is not enforced there.

No JS lint tooling is used while the web UI is the current 4 static files
checked by `make web-check`, with behavioral unit tests for the pure helpers
in `web/common.js` under `make web-test` (`tests/web/`). Revisit if the web UI
grows beyond those files or gains a build step (bundling/transpilation).

## Operations

### Single-instance deployment

zimservice is designed as a **single-instance** service. On startup it acquires a
Postgres advisory lock (`pg_try_advisory_lock`). The `serve` command is a hard
gate on this: if the lock is already held by another instance, a second `serve`
**refuses to start** (non-zero exit before the port is bound) rather than running
side-by-side. The lock protects in-process state that two live servers would
corrupt — the settings cache, the rate limiter, the qBittorrent client cache, and
the ZIM LRU. Set `ZIMSERVICE_ALLOW_MULTI_INSTANCE=1` to override and fall back to
warn-only (not recommended). The read-only subcommands (`list --sync`, `status`,
`index`, `mcp`, `embed`) stay warn-only. For production deployments, run at most
one `serve` per Postgres database.

**`zim_dir` is a per-database guarantee.** The advisory lock is per-database, so it
cannot exclude an instance that runs against a *different* database. If two
instances share `general.zim_dir` across different databases they will
double-install/double-index the same ZIMs (same `zim_dir` on disk, two writers).
Run at most one `serve` per `zim_dir`, not just per database. The server logs a
one-time startup warning about this.

### Pool sizing

The default connection pool size is **20** (`db_pool_size`). All subsystems — the
HTTP API, the download poller, the embedding pipeline, and index COPY operations —
share this single pool. If you experience `429`-like backpressure or pool-wait
timeouts during heavy indexing, consider increasing `db_pool_size` via the
`DB_POOL_SIZE` setting.
The pool has a 10-second wait timeout to fail fast under exhaustion rather than
stalling indefinitely.

### Testing without a database

`make test` runs the full unit test suite. Integration tests that require a live
Postgres instance are skipped gracefully when the database is unreachable. Use
`make test-strict` (which sets `ZIMSERVICE_REQUIRE_DB=1`) to make a missing
database a **hard failure** — this is the gate for CI pipelines with a database
service available.

`make test-strict-perf` runs the DB-gated performance guards (e.g.
`trgm_index_perf_check`): these seed 100k rows and run `EXPLAIN (ANALYZE)` to
catch query-plan regressions (e.g. an accidental seq scan replacing an index
scan). They are `#[ignore]`d by default so the correctness gate
(`test-strict-ci`) stays fast. Run them in a nightly job, not per-PR.

The OpenAPI spec can also be dumped standalone for review or diffing:

```sh
cargo run --example dump_spec
```
